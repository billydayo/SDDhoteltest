## 前置

### 兩個服務各自啟動

前後端是**兩個獨立的行程**，不再是一個 `index.html`。

```bash
# 終端 1：後端（需 backend/.env，見 backend/README.md）
cd backend && uv run uvicorn sunny.main:app --reload      # http://127.0.0.1:8000

# 終端 2：前端
cd frontend && npm run dev                                 # http://localhost:5173
```

前端以相對路徑 `/api/...` 呼叫後端，由 Vite 的開發代理轉過去。因此**瀏覽器只會
看到 `localhost:5173` 一個來源**——Network 面板裡不該出現 `127.0.0.1:8000`。

### 測試帳號

```
會員   guest@sunny.com / guest123
管理員 admin@sunny.com / admin123
```

### 記錄方式

發現問題時記下五件事：哪一頁、做了什麼、預期什麼、實際看到什麼、console 有無紅字。
少了最後一項，回頭重現的成本會高很多。

#### ⚠️ 判準：問「有沒有內容拿不到」，不要問 scrollWidth

兩種直覺的量法都會說謊，而且方向相反：

| 量法 | 為什麼不行 |
|---|---|
| `scrollWidth > clientWidth` | **假陽性**。表格待在自己的 `overflow-x-auto` 裡橫捲是設計如此，`documentElement.scrollWidth` 照樣算進去。實測後台十二個模組全被誤報 |
| `window.scrollX > 0` | **假陰性**。`body` 的 `overflow-x: clip` 會傳播到視窗層，頁面根本捲不動，於是「內容被裁掉且拿不回來」看起來跟沒事一樣 |

正確的問法：某個元素超出視窗了嗎？若是，往上找有沒有一個**本身在視窗內**的
可橫向捲動祖先。有 → 使用者捲得到；沒有 → 那段內容就是不見了。

這個差別不是理論。後台導覽列在 `AdminLayout` 補上 `min-w-0` 之前，320px 下
超出的七個模組既沒有捲軸也捲不到——**使用者點不到它們**，而 `window.scrollX`
從頭到尾都是 0。

### C1. Console 零錯誤零警告（T181、SC-014）

- [x] **前端 console：126 次頁面載入零紅字、零黃字**（2026-08-04，21 頁 × 6 寬度，
      含 React 的 key 警告在內）
- [ ] 走訪時**操作**每一頁（送出表單、切分頁、開對話框）後 console 仍乾淨——
      上面那次只驗了「載入」，互動時才出現的警告不在其中。

      2026-08-04 第二次嘗試：走查腳本已經寫好（登入錯誤路徑 → 正確登入 →
      首頁四種篩選 → 房源詳情 → 訂單分頁與取消的二次確認 → 退款表單的空原因
      → 收藏／訊息／帳戶／安全檢測／條款 → 404 與不存在的房源 id），每一步
      都有斷言，找不到那顆按鈕就中斷。**跑到 C1「進入第一間房源」就斷了**，
      因為房源請求收到 500——成因與下一項同一個，見下。

      量到而且站得住的部分：
      - 密碼錯誤時畫面出現 `role="alert"`，內容是「電子郵件或密碼錯誤。」——
        **沒有指出是哪一欄錯**，符合 Login.tsx 的設計意圖與 FR-013。
      - 除了刻意觸發的那個 401 之外，前端沒有噴出任何自己寫的紅字或黃字。
      - 另有 9 筆 `ERR_ABORTED`，全部落在登入後與換頁時的 in-flight 請求上；
        這是 React Query 在元件卸載時取消請求的正常行為，**不是錯誤**。

      分類是必要的：Chrome 對任何非 2xx 都會自己印一行 "Failed to load
      resource"。把那一行算成「console 紅字」的話，任何錯誤路徑的測試都
      永遠不會通過——而錯誤路徑正是最該走的地方。
- [ ] **⚠️ 後端日誌尚未乾淨地驗過。** 2026-08-04 那一輪日誌裡有 82 次未處理例外
      與 53 個 500，成因全部是同一件事：

      asyncpg.exceptions.InternalServerError:
      (EMAXCONNSESSION) max clients reached in session mode
      - max clients are limited to pool_size: 15

      Supabase Session pooler 只給 15 個連線，而當時同時開著四個 uvicorn、一輪
      pytest 與兩支 puppeteer 稽核。**這是測試環境的容量問題，不是程式缺陷**——
      要重驗這一項，得只開一個後端、且沒有其他測試在跑。

      2026-08-04 第二次嘗試：重啟成單一後端、日誌另存，走查期間仍有 16 次
      例外，**全部是同一個 `EMAXCONNSESSION`，沒有任何應用邏輯的例外**。
      算得出來為什麼：`db.py` 每個 uvicorn 是 `pool_size=5, max_overflow=5`，
      而機器上另外還開著三個後端（連接埠 8011／8012／8013）。三台就算完全
      閒置也各自握著五條連線，15 個位子在我這台開口之前就滿了。

      正式環境是單一程序，10 ≤ 15，這個設定沒有問題。**要收掉這一項，
      唯一的前提是同一時間只有一個後端連著那個 pooler。**

      附帶的好消息：`main.py` 的 catch-all handler 表現正確——用戶端拿到的是
      乾淨的 `INTERNAL_ERROR`，**堆疊只留在伺服器日誌**（FR-074），而前端在
      `/me` 與 `/site-content` 收到 500 時沒有變成白畫面（FR-084）。

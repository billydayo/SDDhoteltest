## ⚠️ 這份清單的界線

**只放自動化做不到的事。**

舊清單的教訓是：15 項裡有一半後來被自動化接手，但清單沒有跟著縮短，於是每次
驗收都在重做機器已經做過的事——而真正需要人眼的那幾項反而淹沒在裡面。

因此本清單只收三類：

1. **需要真實外部帳號**（Google OAuth 往返）
2. **需要人眼判斷**（版面、對比、文案是否讀得懂）
3. **需要真實瀏覽器**（console 訊息、Network 面板、檔案下載、重新整理與上一頁）

其餘一律由自動化承擔，並在下方「已由自動化覆蓋」逐條指名是哪一支。
**看到那一節裡的項目時不要重做**——去讀那支測試比手動點一次可靠。

## 前置

### 兩個服務各自啟動

前後端是**兩個獨立的行程**，不再是一個 `index.html`。

```bash
# 終端 1：後端（需 backend/.env，見 backend/README.md）
cd backend && uv run uvicorn sunny.main:app --reload      # http://127.0.0.1:8000

# 終端 2：前端
cd frontend && npm run dev                                 # http://localhost:5173
```

前端以相對路徑 `/api/...` 呼叫後端，由 Vite 的開發代理轉過去。因此**瀏覽器只會
看到 `localhost:5173` 一個來源**——Network 面板裡不該出現 `127.0.0.1:8000`。

### 測試帳號

```
會員   guest@sunny.com / guest123
管理員 admin@sunny.com / admin123
```

### 兩支稽核腳本（先跑它們，再開始用人眼看）

```bash
# 21 頁 × 6 個寬度：內容有沒有被裁掉、每次載入的 console
node specs/001-booking-site/checklists/responsive-audit.mjs

# 互動走查：登入錯誤路徑、篩選、訂單、退款表單、404
node specs/001-booking-site/checklists/t181-walkthrough.mjs
```

**零 npm 相依**——只用 Node 內建的 WebSocket 驅動 Chrome（`lib/cdp.mjs`），
不需要 `npm install`，也不需要 puppeteer。前提只有兩個：Node 22 以上、
機器上有 Chrome（找不到時設 `SUNNY_CHROME` 指路）。

兩支都以結束碼表示結果，各自把完整結果寫成同目錄的 JSON。
`SUNNY_HEADFUL=1` 可以看著它跑。

> 2026-08-05：這兩支原本一支在暫存目錄、一支寫死了別台機器的 puppeteer 路徑，
> 因此都活不過一次關機。稽核腳本活得比工作副本久，就不能相依於工作副本裡的東西。

#### ⚠️ 判準：問「有沒有內容拿不到」，不要問 scrollWidth

兩種直覺的量法都會說謊，而且方向相反：

| 量法 | 為什麼不行 |
|---|---|
| `scrollWidth > clientWidth` | **假陽性**。表格待在自己的 `overflow-x-auto` 裡橫捲是設計如此，`documentElement.scrollWidth` 照樣算進去。實測後台十二個模組全被誤報 |
| `window.scrollX > 0` | **假陰性**。`body` 的 `overflow-x: clip` 會傳播到視窗層，頁面根本捲不動，於是「內容被裁掉且拿不回來」看起來跟沒事一樣 |

#### ⚠️ 捲軸：稽核時 MUST NOT 用 `--hide-scrollbars`

2026-08-05 踩到，值得寫下來。開著 `--hide-scrollbars` 跑，320px 會真的是
320px，`innerWidth`、`clientWidth`、`100vw` 三者一致，看起來乾淨——但**版面的
containing block 仍然扣掉了捲軸那 15px**。於是首頁主視覺被量成「向左偏 7px」
（7 就是 15/2），六個寬度各報一筆，共 6 筆全是假的。

關掉之後同一個元素是 `left: 0`、`width: clientWidth`，分毫不差。

判準跟上面同一條：**要量的是使用者真正看到的版面，而使用者的瀏覽器有捲軸。**
把捲軸藏起來等於在量一個沒有人會看到的版面。`lib/cdp.mjs` 因此預設不藏。

正確的問法：某個元素超出視窗了嗎？若是，往上找有沒有一個**本身在視窗內**的
可橫向捲動祖先。有 → 使用者捲得到；沒有 → 那段內容就是不見了。

這個差別不是理論。後台導覽列在 `AdminLayout` 補上 `min-w-0` 之前，320px 下
超出的七個模組既沒有捲軸也捲不到——**使用者點不到它們**，而 `window.scrollX`
從頭到尾都是 0。

      Dockerfile 因此把 `--workers` 固定為 1）。

      2026-08-04 那一輪日誌裡有 82 次未處理例外與 53 個 500，成因全部是同一件事：

      asyncpg.exceptions.InternalServerError:
      (EMAXCONNSESSION) max clients reached in session mode
      - max clients are limited to pool_size: 15

      Supabase Session pooler 只給 15 個連線，而當時同時開著四個 uvicorn、一輪

      正式環境是單一程序，10 ≤ 15，這個設定沒有問題。**要收掉這一項，
      唯一的前提是同一時間只有一個後端連著那個 pooler。**

      附帶的好消息：`main.py` 的 catch-all handler 表現正確——用戶端拿到的是

## D. 十二個故事的走訪

每一項都是「照著使用者會走的路走一次」，重點在**串起來之後有沒有斷掉**——
單元測試驗的是每一段，這裡驗的是接縫。

- [ ] **US1 瀏覽與搜尋**：從首頁篩選到詳情頁，房態顯示與所選日期一致
- [ ] **US2 註冊與登入**：註冊 → 登入 → 改個人資料 → 登出 → 再登入，資料還在
- [ ] **US3 訂房**：三步驟走完 → 訂單確認頁七項資訊齊全 → 倒數會動
- [ ] **US4 訂單與退款**：在**列表上**直接付款、在**列表上**直接取消

## ⚠️ 這份清單的界線

**只放自動化做不到的事。**

舊清單的教訓是：15 項裡有一半後來被自動化接手，但清單沒有跟著縮短，於是每次

1. **需要真實外部帳號**（Google OAuth 往返）
2. **需要人眼判斷**（版面、對比、文案是否讀得懂）

其餘一律由自動化承擔，並在下方「已由自動化覆蓋」逐條指名是哪一支。
**看到那一節裡的項目時不要重做**——去讀那支測試比手動點一次可靠。

## 前置

### 要在哪裡驗？兩個選擇

**選項 1（推薦）：直接用正式站。**

```
https://sunny.odootpe.org
```

不必安裝任何東西，只要一個瀏覽器。整份清單除了「第 0 關」之外都可以在這裡做完，
而且驗的就是使用者真正會看到的東西。

⚠️ 兩個代價，做之前要知道：

- **你的操作會留下真實資料。** 建立的訂單、送出的評論與訊息都會留在資料庫裡，
  其他人看得到。做完後可以在「後台 → 系統參數 → 還原示範資料」清乾淨，
  但那會**一併清掉別人留下的東西**，動手前先問一聲。
- **第 0 關（後端沒開）在正式站做不到**，後端一直開著。那一關要用選項 2。

**選項 2：在自己電腦上跑。**

前後端是**兩個獨立的行程**，不是一個 `index.html`。

```bash
# 終端 1：後端（需 backend/.env，見 backend/README.md）
cd backend && uv run uvicorn sunny.main:app --reload      # http://127.0.0.1:8000

# 終端 2：前端
cd frontend && npm run dev                                 # http://localhost:5173
```

前端以相對路徑 `/api/...` 呼叫後端，由 Vite 的開發代理轉過去。因此**瀏覽器只會
看到 `localhost:5173` 一個來源**——Network 面板裡不該出現 `127.0.0.1:8000`。

### 你需要會開的三個工具

整份清單只用到瀏覽器內建的功能，不必裝東西。按 **F12** 打開開發者工具後：

| 面板 | 用來做什麼 | 這份清單哪裡會用到 |
|---|---|---|
| **Console** | 看網頁有沒有噴紅字（錯誤）或黃字（警告） | C1、D 節全程開著 |
| **Network** | 看網頁跟伺服器要了什麼、回了什麼 | A、C2、C3 |
| **裝置模擬**（Ctrl+Shift+M） | 把視窗變成手機寬度 | B1、B2 |

> **「紅字」是什麼意思？** Console 裡的訊息分顏色：紅色是錯誤、黃色是警告、
> 灰白是一般訊息。正常操作下**紅字與黃字都應該是零**。看到紅字先別緊張——
> 記下它那一行寫什麼，那句話就是回報問題時最重要的線索。

### 記錄方式

**打勾就是打勾，別勾「大概沒問題」。** 沒把握的項目留空並寫一句為什麼——
一個誠實的空格比一個心虛的勾有用得多。

發現問題時，照這張表填。**五欄都要填**，尤其最後一欄：

| 欄位 | 例子 |
|---|---|
| 哪一項 | D3 步驟 6 |
| 哪一頁 | `/booking/確認頁` |
| 我做了什麼 | 選 LINE Pay，按送出 |
| 預期看到 | 訂單成立，狀態「待付款」，有倒數 |
| 實際看到 | 停在轉圈，10 秒後沒有反應 |
| **Console 有沒有紅字** | 有：`Failed to fetch /api/orders` |

最後一欄常被跳過，但**它是唯一能讓別人重現問題的線索**。畫面上的症狀通常
只說明「壞了」，console 那行字才說明「哪裡壞了」。

沒有紅字也要寫「無」——「沒寫」和「沒有」是兩件事。

      2026-08-05 重測仍在，且**只剩這一項**：126 次量測其餘全數乾淨。
      數字由 129px 改為 136px，差的 7px 是捲軸——見下方「捲軸」。

#### ⚠️ 判準：問「有沒有內容拿不到」，不要問 scrollWidth

兩種直覺的量法都會說謊，而且方向相反：

| 量法 | 為什麼不行 |
|---|---|
| `scrollWidth > clientWidth` | **假陽性**。表格待在自己的 `overflow-x-auto` 裡橫捲是設計如此，`documentElement.scrollWidth` 照樣算進去。實測後台十二個模組全被誤報 |
| `window.scrollX > 0` | **假陰性**。`body` 的 `overflow-x: clip` 會傳播到視窗層，頁面根本捲不動，於是「內容被裁掉且拿不回來」看起來跟沒事一樣 |

#### ⚠️ 捲軸：稽核時 MUST NOT 用 `--hide-scrollbars`

2026-08-05 踩到，值得寫下來。開著 `--hide-scrollbars` 跑，320px 會真的是
320px，`innerWidth`、`clientWidth`、`100vw` 三者一致，看起來乾淨——但**版面的
containing block 仍然扣掉了捲軸那 15px**。於是首頁主視覺被量成「向左偏 7px」
（7 就是 15/2），六個寬度各報一筆，共 6 筆全是假的。

關掉之後同一個元素是 `left: 0`、`width: clientWidth`，分毫不差。

判準跟上面同一條：**要量的是使用者真正看到的版面，而使用者的瀏覽器有捲軸。**
把捲軸藏起來等於在量一個沒有人會看到的版面。`lib/cdp.mjs` 因此預設不藏。

正確的問法：某個元素超出視窗了嗎？若是，往上找有沒有一個**本身在視窗內**的
可橫向捲動祖先。有 → 使用者捲得到；沒有 → 那段內容就是不見了。

這個差別不是理論。後台導覽列在 `AdminLayout` 補上 `min-w-0` 之前，320px 下
超出的七個模組既沒有捲軸也捲不到——**使用者點不到它們**，而 `window.scrollX`
從頭到尾都是 0。

### B3. 文案（FR-069、FR-075）

**B3-1 錯誤訊息說得出下一步**

一句「失敗」對使用者沒有用。逐一觸發下面三個錯誤，看訊息有沒有告訴他該做什麼：

1. 登入頁輸入錯的密碼
   - [ ] 訊息讀得懂，而且**沒有指出是帳號錯還是密碼錯**
     （這是刻意的，見 FR-004——指出來等於幫人試出哪些 email 有註冊）
2. 註冊頁密碼只填 3 個字
   - [ ] 明確說出「至少 6 個字元」，而且**游標自動跳到密碼欄**
3. 訂房時把入住日選成今天
   - [ ] 明確說出「需提前一天，最早可選明日」

**B3-2 沒有開發用語外洩**

使用者不該看到程式語言的詞彙。全站走一輪，特別注意數字與空白的地方：

- [ ] 沒有出現 `null`、`undefined`、`NaN`、`Error:`、`[object Object]`
- [ ] 沒有出現英文的例外名稱（`TypeError`、`ValidationError` 之類）
- [ ] 沒有出現檔案路徑或 SQL 語句

> 最容易出現的地方是「還沒有資料」的欄位：平均評分應該顯示「尚無評分」而不是
> `0` 或 `NaN`，金額算不出來時應該顯示 `—`。

**B3-3 空狀態有引導**

「沒有資料」和「壞掉了」在畫面上很容易長得一樣。

1. 用一個全新帳號登入（或用 guest 但先確認清單是空的）
2. 逐一開這四頁，每一頁都要 - [ ] **有一句話說明現在是空的，並且給得出下一步**：
   - `/favorites`（我的收藏）
   - `/orders`（我的訂單）
   - `/messages`（客服訊息）
   - 首頁搜尋一個不可能有結果的條件（例如價格上限填 1）
3. - [ ] 四頁都**不是**一片空白，也不是只有一句「沒有資料」

      `controller.abort()` 的正常行為。**沒有任何應用程式自己噴的紅字或黃字。**

      2026-08-04 兩次嘗試都停在 C1「進入第一間房源」（房源請求收到 500），
      成因見下一項。今天能走完的差別只有一個：資料庫換成本機的 PostgreSQL，
      沒有 pooler，也就沒有連線配額可搶。

      量到而且站得住的部分：
      - 密碼錯誤時畫面出現 `role="alert"`，內容是「電子郵件或密碼錯誤。」——
        **沒有指出是哪一欄錯**，符合 Login.tsx 的設計意圖與 FR-013。
      - 除了刻意觸發的那個 401 之外，前端沒有噴出任何自己寫的紅字或黃字。
      - 另有 9 筆 `ERR_ABORTED`，全部落在登入後與換頁時的 in-flight 請求上；
        這是 `useAsync`／`AuthContext` 在元件卸載時 `controller.abort()` 的
        正常行為，**不是錯誤**。（2026-08-05 更正：原文寫成 React Query，
        但這個專案並沒有這個相依。）

      分類是必要的：Chrome 對任何非 2xx 都會自己印一行 "Failed to load
      resource"。把那一行算成「console 紅字」的話，任何錯誤路徑的測試都
      永遠不會通過——而錯誤路徑正是最該走的地方。
- [x] **後端日誌乾淨。2026-08-05 驗過：685 行日誌，0 次 Traceback、0 個 ERROR、
      0 個 500、0 次 `EMAXCONNSESSION`。** 非 2xx 只有三筆，全部是走查刻意觸發的
      （兩次 401 密碼錯誤、一次 404 不存在的房源 id）。

      環境：本機 PostgreSQL 17.6（`btree_gist` 已裝）、單一 uvicorn、
      `SUNNY_TEST_DATABASE_URL` 指向另一個資料庫。同一輪 `uv run pytest` 583 項
      全過——**這是這些測試第一次真的跑到**，先前未設該變數時它們是跳過的
      （跳過也是綠的，見 `.env.example` 對這一點的警告）。

      以下保留 2026-08-04 的紀錄，因為那個成因會在正式環境以另一種形式回來
      （見 `docs/deploy.md`：DO Managed Postgres 最小方案上限 22 條，
      Dockerfile 因此把 `--workers` 固定為 1）。

      2026-08-04 那一輪日誌裡有 82 次未處理例外與 53 個 500，成因全部是同一件事：

      asyncpg.exceptions.InternalServerError:
      (EMAXCONNSESSION) max clients reached in session mode
      - max clients are limited to pool_size: 15

      Supabase Session pooler 只給 15 個連線，而當時同時開著四個 uvicorn、一輪
      pytest 與兩支 puppeteer 稽核。**這是測試環境的容量問題，不是程式缺陷**——
      要重驗這一項，得只開一個後端、且沒有其他測試在跑。

      2026-08-04 第二次嘗試：重啟成單一後端、日誌另存，走查期間仍有 16 次
      例外，**全部是同一個 `EMAXCONNSESSION`，沒有任何應用邏輯的例外**。
      算得出來為什麼：`db.py` 每個 uvicorn 是 `pool_size=5, max_overflow=5`，
      而機器上另外還開著三個後端（連接埠 8011／8012／8013）。三台就算完全
      閒置也各自握著五條連線，15 個位子在我這台開口之前就滿了。

      正式環境是單一程序，10 ≤ 15，這個設定沒有問題。**要收掉這一項，
      唯一的前提是同一時間只有一個後端連著那個 pooler。**

      附帶的好消息：`main.py` 的 catch-all handler 表現正確——用戶端拿到的是
      乾淨的 `INTERNAL_ERROR`，**堆疊只留在伺服器日誌**（FR-074），而前端在
      `/me` 與 `/site-content` 收到 500 時沒有變成白畫面（FR-084）。

一個人從頭走完約 **2.5 至 4 小時**，可以分次做。粗略分配：

| 區塊 | 約需 | 要準備什麼 |

| D（十二個故事） | 60–90 分 | 兩個瀏覽器（C5 要） |

**建議分兩次**：第一次做前置 + A + B + C，第二次做 D——D 是一條連續的線，
中途被打斷要重來一段。

### 不會做的項目怎麼辦

- **留空，並在旁邊寫一句為什麼**。不要猜、不要「看起來應該沒問題」就打勾。
- 需要別人幫忙的（例如 C5 要第二台裝置、A 要 Google 帳號）就標記「待協助」，
  不要因為做不到就跳過。

   會影響主要流程的問題，自動化測試早就抓到了。留給人眼的，正是那些「不影響

**Date**: 2026-08-04 | **來源**: [tasks.md](./tasks.md)（192 項，已完成 57 項）

> **本文件不重述任務內容，只指派編號。** 任務的描述、檔案路徑與驗收條件一律以
> `tasks.md` 為準。複製一份任務清單過來就會產生第二份事實來源，而兩份必然分歧

## 分派原則

剩餘 **135 項**。切法依三個判準，優先順序如下：

1. **相依鏈不可跨線切斷**。`US1 → US2 → US3 → US4 → US5` 是一條會員端主鏈，
   `US6 → US7/US8/US11/US12` 是後台鏈。把一條鏈切在兩台之間，等待就變成常態。
2. **每條線開工當下就有事做**。兩線都不必等對方交東西才能開始。
3. **檔案擁有權盡量單一**。同一個檔案被兩台同時改是合併衝突的唯一來源。

平均分配是第四順位，不是第一——為了湊數字而拆開一條相依鏈，省下的工時會在等待與
合併衝突裡還回去。

| 線 | 主題 | 任務數 |
|---|---|---|
| **甲** | 會員端主鏈：前端骨架 + US1 + US2 + US3 + US4 + US5 | 68 |
| **乙** | 管理端與加值：US6 + US7 + US8 + US9 + US10 + US11 + US12 + 訊息 | 61 |
| （會合） | 收尾六項，兩線都完成後一起做 | 6 |

**切在「會員端 / 管理端」而不是「前端 / 後端」**：後者看起來更整齊，但每個故事都要
兩台都做完才能驗收，`browser-acceptance.md` 的關卡就一關都收不掉。整份 `tasks.md`
是按「每個故事獨立可交付」組織的，照層切會把那個性質丟掉。

兩台切法的一個實質好處是衝突面比三台小得多：`RoomDetail.tsx`（US1 + US5）、
`routers/rooms.py`（US1 + US5）、`routers/orders.py`（US3 + US4）、
`admin_rooms.py` 與 `room_photos.py`（US6 + US9）——這五個原本的熱點現在都各自
落在同一條線內，不再跨線。

剩下真正的交界只有四個：

| 檔案 | 建立 | 之後誰改 | 建議 |
|---|---|---|---|
| `frontend/src/api/types.ts` | 甲 T039 | 乙加後台型別 | 只 append、不重排 |
| `frontend/src/router.tsx` | 甲 T040 | 乙註冊後台路由 | 只 append、不重排 |
| `frontend/src/components/RoomCard.tsx` | 甲 T054 | 乙 T152 加收藏星號 | 乙等甲 push 完再拉 |

「只 append、不重排」這條約定，會讓衝突退化成幾乎必定可自動合併的形式。

## 兩台機器的共用規則

這五條與程式無關，但沒講清楚會直接讓人互相破壞資料。

### 1. 資料庫：一台一個，不可共用

後端測試需要真正的 PostgreSQL（`EXCLUDE USING gist` 不能以 SQLite 替代）。
`conftest.py` 的 `clean_tables` 會執行 `truncate ... cascade`——兩台指同一個資料庫
會把對方的測試資料清掉。

- 每台設**不同的** `SUNNY_TEST_DATABASE_URL`（各自本機 Postgres，或各開一個 Supabase 專案）
- 未設定時測試會**跳過**而非連上開發資料庫，這是刻意的設計，不要改掉它
- 每台的資料庫都要先 `create extension btree_gist`

### 2. Alembic：一次只有一台碰

資料庫版本是資料庫自己記的。兩台各產一支 revision 會出現兩個 head，
之後 `upgrade head` 直接報錯。

- 要加 migration 先講一聲，做完立刻 push
- **`0001_initial.py` 已經在正式庫跑過了，不可再改**，只能加新 revision

### 3. Lockfile：無法手動合併

`backend/uv.lock`（1210 行）與 `frontend/package-lock.json` 都在版控，衝突時不是靠讀 diff
能解的。要加套件先講一聲、加完立刻 push。

### 4. `.env` 不進版控

`.gitignore` 擋掉 `.env` 與 `.env.*`，只放行 `.env.example`。每台自己填一份。
`config.py` 缺變數會在啟動時明確失敗，所以不會有「少一個變數但跑起來了」的模糊狀態。

### 5. Git

一台一個 branch，都從 `python-impl` 開：

```
python-impl
├── track-a/member     甲
└── track-b/admin      乙
```

不要兩台同時直接推 `python-impl`。每完成一個故事就合回主線一次，不要累積到最後
——整份任務清單是按「每個故事獨立可交付」組織的，累積合併會讓那個性質消失。

## 進度回寫

`tasks.md` 的核取方塊是兩線共用的。改它必然衝突，因此約定：

- 完成一個**故事**（不是單一任務）才回寫一次 `tasks.md`
- 回寫前先 `git pull`
- 只勾自己那幾行，不要順手整理格式或重排——那會把整段變成衝突
